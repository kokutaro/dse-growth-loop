2026-10-03。ユーザーが追加質問・正解ラベルをレビュー済みとして承認した。質問追加依頼に基づき、[レビュー票](review.md)、[原本](sources.md)、[暫定dataset](dataset.json)を作成した。旧 `evaluation-v1`、送信計画、ゲート、実測証跡は上書きしていない。本承認後、固定計画に基づく実JEV分類を実行する。LLM再順位付けは別途未実施。

正解ありは5分野（software、mechanical、sales、manufacturing、operations）×4課題／分割。調整・確認には異なる作業課題を置き、同一課題の言い換えだけを質問数として増やしていない。確認の正解あり20問をHitRateの分母にできる規模を用意したが、人手ラベルは承認済み。合成集合の実務代表性・統計的独立性は別途検証が必要。これだけで最終HitRate@5測定を完了したことにはならない。LLM再順位付けも別途必要。

課題ごとに直接候補・補助候補・語は一致するが実践のない候補を置き、各分割60資料、全120資料を作った。同種別30候補の全件判定を質問ごとに保存し、40の正解あり質問で2候補ずつ関連度3/2を提案している。残る候補を0とする案も、原本を参照して漏れを確認する必要がある。資料は全て架空で、AIが作った暫定正解をAI検索の正解として自動承認しない。

分類値・Noul・検索語は空で、旧集合の比較結果へ合わせ込んだ値を入れていない。`saved-responses.json` も空の未実行コレクションで、生成した順位を実LLM応答として扱わない。全質問は `smoke=false` の確認/調整用大集合として扱う。既存v1は権限・撤回・複数職歴等の固定回帰用として維持し、本集合の質問に混ぜて独立数を水増ししない。

## 確認したこと

- 全48質問の本文/IDは重複0、既存v1の質問本文・資料群IDとの重複0。
- 分割ごとの正解あり20／正解なし4、人物/事例別件数、分野別件数を確認。
- 全1,440候補判定の対象集合と正解ID・原本根拠を照合。
- 評価器の構造検証を通過後、`humanReviewStatus=pending` によるJEV送信計画生成拒否を確認。これは承認前の確認記録。現在はラベル承認後に送信計画を固定した。
- JSON構文・差分空白を確認。実検索の品質測定は未実施。

## 承認後の順序

1. レビュー票に基づき質問・全候補関連度・根拠・分割を人が確認する。修正があれば質問ID/候補IDで残す。
2. 承認集合として版を固定し、実JEV送信計画・件数/費用予約と新しいdataset/replay hashのゲートを生成する。旧ゲートの承認を新datasetへ自動継承しない。CLIの `--specs docs/specs` で契約パスを明示できる。
3. 語一致と実JEVの比較をまず調整集合で行う。採用候補の条件を確認結果を見る前に固定する。
4. 未使用の確認20問＋正解なし4問を評価する。人物/事例別Recall・HitRate、Noul増分、上限損失、候補の増加を報告する。最終順位の指標は実LLM実行まで未測定とする。

現行の文書/全体重複排除なら単位120＋質問48で最大168固有分類が見込まれるが、実際の送信計画と単価による予約を承認後に再確認する。今回は計画生成のために承認フラグを一時的に変更していない。

## 送信前の固定

[送信計画](jev-plan.json)は168件、jev-1.13.0、[ゲート](gates.json)は一次Recall90%・ウォーム15秒・予算8,000円を維持。[選定手順](selection-policy.json)を分類・調整結果の取得前に固定した。調整のEで両種別Recall90%以上の条件のうち、Nと候補数を優先して選び、その共通条件でL/A〜EとFを一度だけ確認する。条件ファイルとそのhash付き最終ゲートは調整後・確認前にコミットする。

本集合の非該当候補は全課題で質問文を含む案内資料で、語一致に厳しい構成である。今回の数字を一般的な実務質問の性能へ外挿しない。旧v1も併記する。
