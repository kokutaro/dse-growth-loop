# ダミー正解集合とオフライン評価器

更新日：2026-10-03（初版：2026-09-26）。Issue #4 の評価基盤。**全入力・分類値・保存応答は合成fixtureであり、AI品質達成や既存試験の実測結果ではない。** 正解ラベルはAIが作成した草案で、2026-10-03のIssue #14対応時にユーザーが承認した。既存のユーザー試験資料も受領待ち。

## 入力と版管理

`evaluation/` に次を保存する。

| ファイル | 内容 |
|---|---|
| `dataset.json` | 固定検索投影、文書群・職歴/事例ID、質問、関連度0〜3、情報不足、根拠ID、調整/確認区分 |
| `documents/tuning.docx`・`final.docx` | 小集合の架空職歴・事例本文。段落抽出用の最小OOXMLパッケージ |
| `documents/tuning.xlsx`・`final.xlsx` | 各集合の全職歴・事例本文。セル位置を根拠として使用 |
| `extraction-expected.json` | 原本SHA-256、段落文字列、シート名、全セル期待値 |
| `contract-records.json` | Issue #3 の `SearchUnit` / `ClassificationResult` 契約に対応する投影・全Probability・別Confidence・根拠参照。`origin=fixture`、AI実行IDは捏造しない |
| `saved-responses.json` | 質問ID・候補上限Nごとの固定再順位応答。モデル版は `fixture-no-model` |
| `review.md` | 全質問・全候補の人向け正解確認票 |
| `gates.template.json` | 採用値が未確定の評価ゲート |

調整群と確認群はそれぞれ架空12名＋3事例の小集合を持つ。大集合では各群へ難しい非該当の150名を加える（各群162名＋3事例）。同じ職歴の複数単位・反復週報・文書群・人物を別の分割に跨がせない。質問の言い換えを使った分割はしない。確認群は独立の案件本文だが生成パターンを共有するため、外的妥当性の検証用データではない。

機械48か月＋ソフト36か月、副分類、低Confidence、平坦分布、経験不明、部署実績のみ、本人訂正、参加不可、権限外、撤回、旧版、反復週報、該当なしを含む。難しい非該当はソフト・引き継ぎという語を含む営業・配送・契約窓口などで、開発経験と区別する。大集合のN比較は人物を対象とし、事例3件はスモーク確認に留める。

`python3 scripts/generate_evaluation.py` でバイト単位に再生成できる。第三者パッケージ・ネットワーク不要。Officeファイルは取込器用のテスト入力で、帳票としての視覚品質を評価する成果物ではない。現時点ではXML抽出との一致を検証しており、未実装の本番取込器の成功とは扱わない。人がラベルを変更する場合は生成スクリプトと生成物を同時に更新する。

## 実行方法

リポジトリルートで実行する。

```sh
# CIと同じ：調整用小集合のみ。クラウドSDK・HTTPクライアントを持たない
dotnet run --project src/Dse.Evaluation -- --out .artifacts/evaluation-smoke

# 調整用大集合は明示的に選択
dotnet run --project src/Dse.Evaluation -- --large --out .artifacts/evaluation-large

# N=20/50/100と複数職歴の明示回帰試験
dotnet test tests/Dse.Tests --filter Category=LargeEvaluation

# Office・契約互換性。既存 tests/contracts/requirements.txt の依存を使用
python3 -m unittest discover -s tests/evaluation
```

CLIの既定は小集合・`tuning`・K=5。`--k 3`、`--data <dir>`、`--out <dir>`を指定できる。`--live` / `--enable-ai` は受け付けず失敗する。大集合のAI全投入とライブ評価は本Issueに含めない。将来のライブ評価は別の明示コマンドと費用承認が必要。

`origin=recorded-ai-response` と実際のモデル/プロンプト版を指定して後続工程の保存済みAI応答を再生することもできる（CLIからの送信は常に0件）。保存応答を差し替える場合、質問IDとNの組、候補IDの一意性・入力集合内であることを検証する。`success` の空順位は該当なし、`refused` / `failed` / `truncated` は障害として別集計する。障害を空の成功へ変換しない。順位の根拠検証・本番AI応答スキーマへの変換は後続 #8/#11。保存応答は本番APIのレスポンスそのものではなく、評価用の最小リプレイ形式である。

既存 `Retriever` を呼び、正本版のfixtureフェンスを通す。ラッパーの `currentActiveVersion` は現在の正本有効版を表し、古い投影内に保存された `activeVersion` と区別する。事例の型名は契約に合わせて `knowledge` を使用する。上限適用前の全IDは同じ検索条件を人物/事例ごとに適用して求める。この方法は上限を変更せず各エンティティを1候補として取得するためで、検索アルゴリズムを評価器内に複製しない。実Cosmosのページング・最新認可・撤回直後の整合性の検証は #5/#9 で行う。

## 指標と分母

二値正解は「関連度2以上かつ情報不足でない」。質問ごとの指標を算出し、人物/事例、難易度、調整/確認、N、Kの組ごとにマクロ平均する。各平均の分母もJSON・CSVに残す。

| 指標 | 定義と例外 |
|---|---|
| Recall@N | 一次候補内正解数 / 全正解数。全正解0はnull |
| HitRate@N | 正解が一次候補に1件以上あるか。全正解0はnull |
| Precision@K | 上位Kに含まれる正解数 / 実際の表示数。表示0はnull |
| nDCG@K | gain=`2^grade-1`、discount=`log2(rank+1)`。理想順位は全判定集合から構成。情報不足のgainは0、全正解0はnull |
| 最終HitRate@K | 最終上位Kに正解があるか。全正解0と応答障害はnull |
| Noul救済 | 上限適用後候補のうち、Noulなしの上限前集合に存在しないID数。正解・非正解（0/1）・情報不足を別計上 |
| 打切り損失 | 上限前に取得できていた正解のうち上限後に消えた数 |
| 該当なし質問の誤推薦率 | 正解0の質問に1件以上表示した割合。情報不足の表示も保守的に誤推薦として扱う |

Noulなし比較を上限前にすることで、救済枠の変動だけで押し出された候補をNoul独自の救済と誤認しない。未知・情報不足を関連度0へ潰さず、Noul追加数と表示数に別列を設ける。応答障害でも一次検索指標は残し、最終順位指標の平均から除外し障害数を必ず併記する。

`report.json` に入力SHA-256、版、検索経路・根拠単位、上限前後の候補ID、Noulなし集合、保存順位と集計を出す。`questions.csv` は質問別、`summary.csv` は分類別。使用量はオフラインなので呼出・トークン・RU・再試行0、実サービス待ち時間はnull。これらは実AIの品質・費用・性能の実測ではない。

手計算テストでは正解a(3), b(2)、非該当c(0)に対し、取得[a,c]、上限前[a,b,c]、表示[c,a]としてRecall=1/2、Precision=1/2、HitRate=1、nDCG=`(7/log2(3))/(7+3/log2(3))`、打切り損失1を確認する。

## 人の確認と最終確認ゲート

1. レビュアーが `review.md` の各ラベルとOffice原文、情報不足、根拠、全件漏れ、分割の独立性を確認する。判断不一致は理由と修正履歴をPRに残す。AI出力を人の確認の代わりにしない。
2. 承認者・確認日・対象データ版をPRと本書に記録し、`humanReviewStatus` を `human-approved` にする。Issue #14対応時にユーザーの明示承認を受け、`human-approved` に変更した。
3. 調整データで閾値・N・救済枠・Kを選ぶ。一次Recallの最低値、構造化精度の最低値、コールド/ウォームp95上限、AI予算上限を決める。2026-09-26時点ではすべて未確定。Issue #14で一次Recall90%・構造化90%・ウォーム15秒・冷起動上限なし・予算8,000円を承認した。最終HitRateの20問中18問は暫定目安であり、一次Recallの合格値へ転用しない。
4. `gates.template.json` を別ファイルへコピーし、全採用値、`approvedBy`、`frozenAt`（UTCのISO 8601）、`status=frozen`、対象dataset/replayのSHA-256を固定してコミットする。**確認集合の初回実行より前のコミット**としてレビュー承認する。fixture版が変わったらゲートも別版として再承認する。
5. `dotnet run --project src/Dse.Evaluation -- --split final --gates <固定済みJSON> --out <保存先>` を実行する。大集合はさらに `--large`。CLIは未承認・空値・不正ハッシュを拒否する。ゲートの固定順序の真正性はGitレビューで確認する。
6. 後続 #14 のライブ計測を承認された条件で行う。失敗後に同じ確認群を見ながら合格値を緩めず、新しい調整サイクルと独立した確認群を作る。

この節の2026-09-26時点では人の正解確認、既存試験の受領、ゲート採用値の決定、確認集合の評価、実AI品質/待ち時間/費用の実測が未完了だった。2026-10-03以降のラベル・ゲート承認と比較実行は[Issue #14の手順](retrieval-experiments.md)を参照。CIのfixture成功でこれらを完了扱いしない。
