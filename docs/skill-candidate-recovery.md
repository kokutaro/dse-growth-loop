# 技能候補の再確認・再収集

## 変更する確認経路

`SkillDictionaryService` は現在の権限、元レコードと全根拠の閲覧・利用条件を毎回検証する。根拠 fingerprint が変わった候補は一覧から除外せず、`sourceStatus: changed` / `reviewable: false` として返す。ただし古い元表現、引用、要素、提案、承認理由を一覧へ返さない。fingerprint は本文・根拠・スコープ・再検証済み技能と検証版を含むため、画面では原因を「根拠または検証版の更新」と表示する。変更の内訳を推測しない。

元資料の削除・撤回・失効した権限は別扱いである。これらは一覧にIDや件数を出さず、直接参照は従来どおり404とする。404で存在・非存在や権限の違いを公開しない。元レコードが読めても現在の根拠を利用できなければ表示しない。

同じ候補レビュー画面の `GET /api/v1/skill-candidates/{id}/source` で、現在アクセスできる本文・根拠、再検証の状態と保留理由を確認する。保留中の未検証引用をそのまま表示しない。抽出語が現在の根拠に含まれる場合だけ語を表示し、見つからない場合はその旨を表示する。本人関与の抽出値は認定結果ではない。

## 収集保留の保存と冪等性

収集時に一部または全部の候補が引用等の検証で保留された場合、既存 `skillCandidate` 保存先に `candidateType: collection` の通知を原子的に保存する。通知は技能ではなく `item` / `element` / `conceptId` がnull、状態は `collection_held`、履歴は空とする。保存するのは元資料ID、fingerprint、入力状態、検証理由と通常の作成メタデータであり、不正な引用は複製しない。正常候補と保留通知は併存できる。

IDは元資料・fingerprintから決まり、同じ収集の再送や異なるキーでの再収集でも二重作成しない。既存のアクセスフェンス・冪等性receiptを使用する。UIも送信中の二重操作を抑止し、応答不明時には同じキー・本文を保って再送する。書込み前に現在の権限と根拠を再検証する。

「現在の根拠で再収集」は既存collect APIに `expectedFingerprint` を渡す。確認後に根拠が更新されていたら409で再確認を要求する。元の候補・安定ID・承認履歴を上書きせず、新しいfingerprintの候補を作る。同じ内容なら既存候補を返す。古い候補と保留通知に対する承認・AI提案・再分類プレビューはサーバーでも拒否する。

## 保持する境界・互換性

- 人の辞書承認、人物経験の認定、知識・希望・計画・他者経験の区別は変更しない。
- Choiceの質問・候補数・閾値・モデル、検索投影、原文抽出、gold、権限設定は変更しない。再収集に追加AIはない。
- 既存候補は変更せず読める。通知は新しい収集から追加される。過去の保留応答だけで候補が保存されていなかった資料は、資料IDからの再収集が必要。自動全件走査・バックフィルはしない。
- 古い承認履歴は保存するが、根拠更新後に古い自由記述を返す履歴APIは許可しない。今回の画面は原文や抽出内容の編集機能ではない。再検証で同じ問題が残れば保留を維持する。
- DB移行や既存データ書換えは不要。旧版へ戻す前には、新しいcollection通知のnull要素を扱えない旧UI/APIへの影響確認が必要であり、無条件のバイナリ巻戻しは推奨しない。

ローカルMock・固定fixtureでの実装検証であり、実AI精度の改善や本番受入は示さない。公開・配信は別の承認対象。
