# 本番共通の架空資料ワークフローの調査・実装方針

## 概要

ユーザーの最新指示は、データだけを架空にし、一連の動作を本番と共通にすること。現在のmain `0da09703`（PR #69）は技能辞書専用の利用者別メモリデモであり、承認と固定版の読み取り照合はできるが、通常の永続投影・自然文AI検索には接続していない。この制約を解消する。過去の成功したAI応答を初期資料に再利用し、新規の取込・訂正は通常の処理を使う。

既存の未追跡 `preflight-report.md` と2つの画面証跡ディレクトリを保持する。現在の作業ルートとリポジトリ内に `.agents/skills` は存在しないため、利用可能な開発標準スキルとリポジトリの `AGENTS.md` を参照した。既存の階層・ストア・サービス構成を維持し、大規模なレイヤー再配置は行わない。

## 調査で判明した接続箇所

|処理|現状|変更対象|
|---|---|---|
|デモ領域|MemoryRecordStore、1時間、停止で消失|永続ストアの利用者別領域、現在認可による再開|
|原文・承認|SkillDictionaryServiceとSourceGuardを使用|同じコードを通常APIから使用|
|技能ID検索|候補の読み取り時照合のみ|版付き技能対応を永続投影へ接続|
|通常検索|SearchUnit.SkillIdsは存在するが承認済み辞書IDを照合しない|Retriever・投影クエリ・現在根拠の検証|
|自然文検索|分類→一次検索→再順位付け|承認済み技能IDの条件と根拠を同じ経路へ接続|
|取込|通常DocumentUploads→QueueNotice→IngestionProcessor→ProfilePipeline|隔離領域をQueue/Workerまで保持|
|訂正・撤回|版・accessVersion・同意をSourceGuardで再確認|技能ID投影でも同じ拒否を維持|

## 実装方針

1. 既存Cosmosの別論理領域へ業務レコードを保存する。通常の共有辞書・資料のパーティションから検索できない構造にし、新たなAzureサービスやIAMを追加しない。
2. 実認証・現在のoperator/member・利用範囲を確認して利用者の領域を決定する。クライアントが任意の利用者・テナントを指定する設計にしない。現在権限を共有ストアで確認し、隔離領域への権限レコード書込みは拒否する。
3. 通常API・業務サービス・Workerを共用し、隔離するのはストアとキューのコンテキスト。画面の通常取込・承認・検索・訂正操作を使う。無効・期限切れの領域を通常共有領域へ切り替えない。
4. AIの実送信・予算・不明結果の再送防止は既存の共通コードを使う。予算台帳は元の共有上限を維持し、利用者の領域作成で費用枠を増やさない。保存応答は不要再送しない。追加の実AIテストは具体的な回数と上限を確認できるまで実行しない。
5. 人の承認を経た技能ID・辞書版・根拠を投影へ保存し、検索時に現在の承認・原文・認可を再確認する。knowledge-onlyは参考資料にだけ使い、本人の実務経験・熟練度へ昇格させない。旧4案は収集保留の履歴として維持する。
6. TDDで永続再開・利用者分離・権限失効・キュー経由・投影・自然文検索・原文訂正／撤回を検証する。ローカルの保存応答／Mock試験、共有実機試験、追加の実AI試験を別々に記録する。

## 受入条件

- 再起動後も以前の架空2資料・辞書版・承認履歴を再開できる。
- 通常の画面・APIから承認→技能ID投影→語／自然文検索→原文根拠を追跡できる。
- 訂正・撤回・権限失効後、古い投影やAI応答を使って引用を復元しない。
- 他の利用者の領域と通常の共有辞書へ混入せず、一般memberがoperator承認を行えない。
- AIの成功済み処理を再送せず、予算・実行台帳・同意確認を維持する。
- Draft PR、CI、レビューを経て共有環境へ反映し、実際の画面で確認した範囲を報告する。

## 確認が必要になり得る操作

現時点ではIAM・セキュリティ設定の追加変更は予定しない。追加の有料推論や予算増額が必要になった場合は、対象・回数・最大量・金額を具体化してから確認する。実データは扱わない。

## 共通処理を確認して追加で判明した範囲

- 技術列などのcontext断片は、人物の経験へ混ぜないために既存ProfilePipelineが主データへの保存を省いていた。通常取込から辞書候補を確認するには、人物経験とは別の原文付き資料断片を永続化する必要がある。
- 通常Document APIには原本取得と取込・retryがあるが、所有者が原文を訂正・撤回する汎用画面／APIがない。管理用の架空人物専用routeへ迂回せず、通常の認可・ETag・冪等性を使う文書ライフサイクルを追加する。
- 隔離はストレージアドレスだけを変え、論理的なactor/tenantは維持する。実認可レコードはコピーせず、現在の所有者・役割・scope・世代を確認して領域用の認可tokenを導出する。実権限変更のfenceは通常領域と共有し、キャッシュはその正確なfenceの有効期間内だけで使う。
- 承認は候補・監査・辞書版・投影head・SearchUnitを同じcatalogトランザクションで保存する。元の原文・実績レコードは書き換えない。古い投影は保持し、現在headと現在原文を再確認してから検索する。
- 共有前の実装検証では永続分離・通常Worker・投影・自然文検索をMockまたはオフラインtransportで実行している。正常応答のキャッシュは実際のAiServiceで確認し、同じ2回の検索で送信は分類・再順位付けの計2回に留まった。実AI品質の結果ではない。
