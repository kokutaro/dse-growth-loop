# Issue 30：独立24問・本番サービス／HTTP検証

2026-10-03。**本番採用の品質判定は不合格**。副業務断片追加と事例上限15の構成を、ユーザーが承認した新しい架空24問で検証した。既観察48問の100%を本番へそのまま外挿できないことを確認した。

## 条件と独立性

新規10シナリオ、人物30／事例30、正解あり20問と正解なし4問。[承認済み質問・ラベル](../../../evaluation/issue-30/independent/review.md)のdirect=3・共同実施support=2を正解とし、案内のみ／他シナリオ=0。旧集合との原文完全一致は0。合成集合であり、実社員や利用者の無作為標本への一般化は行わない。

モデル・閾値・プロンプト・ラベルを評価後に調整していない。[実行前固定条件](execution-plan.json)と[認証修復・実行履歴](recovery-provenance.json)を参照。人物10／事例15、救済2、副業務検索断片あり、Jev 1.13.0、既存Luna6 deployment、出力3,000、入力予約上限16,000、1試行・Job自動再試行なし。通常APIのJWT検証と許可ユーザーを維持し、既存テスターの公開範囲だけ独立集合へ一時変更した。

人物は本番`ProfilePipeline`による実分類・投影、事例は承認済みダミーの既存形式による正本・原本参照と実分類・投影を使う。事例の完全な公開承認ワークフローは対象外。実Cosmos、SourceGuard、AccessFence、Jev、NaturalSearchService、Foundryを通した。第1段階はManaged Identity専用Job、第2段階は本番SPAの既存MSALサインインと実JWTによる24問のHTTP検索。キー／トークンを評価資料へ保存していない。

## 品質結果

対象種別内の順位と、実画面の全候補先頭5件を区別する。対象種別内の指標は、他種別を取り除いた後の先頭5件を評価する。画面上の指標では他種別も表示枠を占め、質問が要求した種別以外は正解と数えない。Precisionは表示件数が5未満なら実件数を分母にした質問単位平均。正解なし4問は正解ありの平均から除外する。

## 既存48問との違いと原因

1. **入力全体の予算を扱う必要がある。** 既存評価は種別ごとに候補をLLMへ渡した。本番は人物・事例を同時取得し、長い本番用ID・原本参照・JSON表現・固定プロンプトも含む。`AiService`はシリアライズしたUTF-8バイト数＋256を保守的入力トークン上界として16,000と比較する。16件の`inputlimit`はモデルの実測入力トークン超過ではなく、ローカルの事前制限。単に候補上限15へ増やすだけでは、再順位付けまで到達しない。
2. **リランク失敗時の表示を変える必要がある。** 現行`NaturalSearchService`は入力上限や根拠検証失敗で未選別の一次候補を表示する。案内のみの非正解や他シナリオも候補として残る。正解なし2問の誤推薦もこの経路で発生した。
3. **検索対象種別を契約に含める必要がある。** 同じ問題の人物と事例が候補に入り、LLM入力に種別が明示されない。成功時も4候補（人物2・事例2）を返す。失敗時は人物優先の一次順が残り、事例の正解が全表示の先頭5件から押し出される。
4. **取得漏れと引用の安定性は別課題として残る。** 営業2問の共同実施人物が一次上限から落ちた。分類・広い分野条件・候補上限が複合するため、現時点でJevの分類単独を原因と断定しない。引用検証失敗は再現性を追加確認する必要がある。

次の改修候補は、対象種別の絞り込みと明示、IDの短縮対応表・候補ごとの引用量を含む**リランク入力全体の予算化**、超過時の分割評価、失敗時の未検証候補を推薦と混同しない表示。上限値だけを引き上げる改善効果は未測定。今回の独立集合を使って調整すると既観察集合になるため、修正後の最終確認にはさらに別集合を使う。
