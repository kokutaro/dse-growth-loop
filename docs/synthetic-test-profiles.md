# 検証専用の架空人物と資料取込

認証ユーザーを増やさず、現在の `member` + `operator` が自分の既存scope内に、データとしての架空人物を登録する。本人向けアップロード／訂正の境界は変更しない。`personAuthority`、Entra binding、ロール、scope付与は作成しない。

## 最小の運用範囲

- `/test-profiles.html` で管理参照・架空表示名・既存scope・合成データ宣言を指定する。登録先は `test-person-<hash>` の専用ID。表示名にはサーバーで `[検証専用・架空]` を付ける。
- 同一operatorにつき通算3名、各1冊、内部スキルシート形式のXLSX・最大2案件に限定する。利用停止しても枠は回復しない。別ファイルでの更新、実在人物の代理登録・統合、管理者の引継ぎは未対応。
- 人物と文書は現在の管理operatorだけが利用できる。通常社員検索・ワークスペースの検索結果から除外し、専用のテスト検索で通常の原文／具体技能検索ロジックを使う。テスト人物に認証主体はなく、会話参加者として承認しない。
- 文書・版・根拠・実績・Job・検索投影・収集候補に合成識別を引き継ぐ。根拠の引用・原本hash・現在版の照合は通常処理を再利用する。期間は案件期間であり、全技能の実施月数や熟練度へ変換しない。
- 辞書の既存候補画面で根拠・保留理由を確認できる。架空人物からの候補は保留／技能ではないとの記録に限定し、共有辞書の新規登録・別名・統合・追加の意味AI提案を拒否する。人物の経験を人手確認済みにせず、goldを更新しない。

## 冪等性・費用枠・失敗

登録参照はtenant・実operator principalで安定ID化し、同一参照の入力が異なる場合は409。同一入力の再送はキーが変わっても同一人物を返す。ファイルは人物ごとに固定タイトル・hashで安定ID化するため、同一ファイルの再送は同一文書／Jobを返す。原本の耐久保存→fence内の人物・文書・版・Job・予算・監査・冪等性receiptの原子コミット→通知の順序を使う。通知失敗は同一ファイル再送で通知を回復できる。原本stagingの孤立ファイルは既存の明示的なcleanup手順の対象であり、自動削除しない。

`syntheticImportBudget` は文書と別の保存行で、Foundry `extractSkills` 2回、Jev `profile-v1` 分類2回を上限とする。最大4 calls/冊・3冊で12 calls。入力／出力枠、モデル・版・設定単価を受理時に固定し、変更時は追加送信を停止する。単一attemptを必須とし、再試行Jobでも枠を補充しない。失敗・結果不明・送信前の後続失敗も予約枠を保守的に消費する。キャッシュは再認可後に使い、追加枠を消費しない。

この局所的な取込枠は既存AiServiceのledger／execution guard／fence／停止スイッチに追加して使う。`AccountingMode` や全体予算を変更せず、廃止した運用上の承認台帳を復活させない。費用表示は設定単価と呼出し・token上限による最大見積であり、実請求・Azure運用費の上限保証ではない。providerの使用量逸脱は既存の停止・要確認に従う。枠を使い切った文書は理由付き保留となり、画面にJob・runsを表示する。自動増額・自動再送はない。

## 撤回と権限失効

利用停止は理由・If-Match・Idempotency-Keyを必須とし、原本・実績・監査を削除せず、activeVersionを外して版を進める。以降のアップロード、retry、根拠利用、候補収集、検索を停止する。workerは管理operatorの現在の権限と人物の状態を再確認し、公開時には読取ETag全体を照合する。AI後の根拠再確認でも親人物の状態を読む。認証時のactorを原文参照へ流用する前にも、fence待機中の権限撤回を考慮して現在の認可を読み直す。権限外の人物・根拠・候補を表示しない。

既存APIの本人用PATCHで検証人物を訂正・確認することはできない。検証人物の登録が実社員認定や人物経験の承認になることもない。希望・知識・未実施等の抽出は既存v2のAI文脈契約・引用検証を維持する。

## 今回の実装から本番検証まで

1. このローカル差分のレビュー、push／Draft PRと自動previewの承認を別途得る。今回の作業には公開・配信を含めない。
2. 通常のCI／レビュー／配信手順で本番へ適用する。設定・認証・scopeの追加は不要。起動・API／Workerの同一image、healthを確認する。
3. 現在の `member` + `operator` と既存scopeで専用画面に接続し、費用見積を確認して合成Aだけを登録・アップロードする。合成人物が実在データでないことはoperatorが入力前に確認する（自動の個人情報判定器ではない）。
4. ingestion／enrichmentの終端、引用、保留、具体技能と検証専用検索を確認し、B/Cへ進む。以前の別ダミー `budget_stopped` 2系列は再開しない。辞書50技能の評価用データも本番辞書へコピーしない。
5. 試験終了は利用停止。途中失敗はJobを確認して既存retryを使うが、枠消費や不明送信を確認せず繰り返さない。費用枠不足・source撤回は自動解除しない。

既存operatorが現在持つ範囲だけで登録できる設計であり、新しい認証・権限付与は要求しない。本番の認証付き操作・実AI・実請求・クラウド障害時の回復はこのローカル検証では未実施。

HK再作成サンプルの自己PRはD35にあり、現行機械読取のD51とは一致しないため未取込。この変更では入力・reader・プロンプトを変更しない。

## 切戻しの注意

検証データをまだ登録していない段階は通常のコード切戻しが可能。登録後は旧版に合成人物のowner境界がないため、単純な旧imageへの切戻しは行わない。人物の利用停止は原本削除ではなく、旧APIでの原本閲覧を制限する保証にもならない。合成ACLを維持する版で回復し、対象データの現在の閲覧範囲を確認する。削除・権限拡大で代替しない。

通常のAzureプレビューはDemo／Mockかつ既定のoperatorがないため、登録の正常系はloopback専用fixtureで確認する。公開プレビューの403を回避するDemo認証変更は行わない。
