## 1. 検証の出発点

Jevの日本語分類の正しさは、ユーザーの試験で目標達成済み。本計画はその結果を前提とし、「複数Probabilityを保存すれば必要な候補が検索集合へ入るか」「補助Noulがどの程度救済するか」「FoundryのLLMが候補を適切に再順位付けできるか」を測る。

既存試験のデータ・質問・選択肢・モデル版・結果を受領して回帰用に保存する。未共有の精度値は埋めない。すべてダミーデータを用い、人物検索と事例検索の結果は別集計とする。

## 2. 比較する構成

| 構成 | 変更点 | 調べたいこと |
|---|---|---|
| A | 人物/事例全体のChoice最上位のみ | 比較用の取りこぼし基準。採用案ではない |
| B | 全分布から複数Probabilityを検索 | 非最上位カテゴリによる救済 |
| C | Bに職歴・案件・事例断片単位の分類を追加 | 主分野でない実経験の救済 |
| D | CにNoulの経験有無経路をOR追加 | 追加で救える候補と費用 |
| E | Dに正規化語・スキルIDの経路をOR追加 | 辞書・語一致の補完効果。初期の本命構成 |
| F | 権限内の全候補を評価 | 少数データでの検索段階の比較基準。LLMの正しさを保証するoracleではない |

各構成で質問側も最上位限定/複数カテゴリ展開を比較する。変更点を一度に増やさず、保存単位・閾値・Noul・語一致の効果を分ける。一次検索だけの比較と、同一候補集合に対するLLM再順位付け比較を両方行う。

## 3. 正解データ

クエリごとに関連する人物ID/事例IDを人が列挙し、関連度を0（非該当）、1（周辺・参考）、2（有用）、3（直接適合）で付ける。二値指標で正解とする関連度は2以上を仮定する。情報不足は別の印を付け、非該当と混ぜない。

分類結果やLLM出力そのものを正解ラベルにしない。正解集合の漏れを点検し、判断が分かれる例は理由付きで合議する。閾値調整用と最終確認用を分け、似た資料・同一職歴の言い換えが両方へ漏れないようにする。

必須ケース：

- 機械系4年・ソフト系3年の人を、ソフト系の課題で検索する。
- 同一事例が複数業種・課題種別に関連し、最上位ではない分野からも見つかる。
- 分布が分散してConfidenceが低いが、有用な副分類を持つ。
- 大きな分類体系で一つひとつのProbabilityが小さく、固定閾値だけでは落ちる。
- 職歴が多い人と少ない人。職歴数や文書量の多さだけで候補枠を独占しない。
- 未知分野、情報不足、経験なし、用語だけ記載、部署実績のみ、本人訂正後。
- 語は似ているが問題・役割が異なる非該当例。必要な経験はあるが本人は参加不可。
- 非公開資料、公開撤回直後、重複した週報、古い版。
- 該当する人物/事例が一つもない質問。

初期の12名等の小規模データではN=20でも全件となり、絞り込みの比較にならない。その場合は全件との差を確認するスモーク試験と位置付ける。N=20/50/100の差を測る段階では、同じ用語を含む難しい非該当例を加え、ユニークな候補総数を最大Nより十分多くする。大量の無関係なダミーだけで容易な試験にしない。

## 4. 保存・検索契約

分類分布の正本には次を残す：`unitId`, `axis`, `choice`, `probabilities`, `confidence`, `sourceRefs`, `taxonomyVersion`, `promptVersion`, `modelVersion`, `inputHash`。

Noulは別に`signalId`, `yesProbability`, `evidenceState`, `sourceRefs`, `questionVersion`, `modelVersion`を保存する。未評価はNULL/未評価状態とし、0へ変換しない。経験期間は抽出した年月からコードで計算し、どちらの確率からも逆算しない。

概念例（数値はユーザーの説明に沿った仮例で、測定結果ではない）：

```json
{
  "entityId": "person-demo-01",
  "unitId": "profile-summary",
  "classifications": [
    { "axis": "domain", "categoryId": "mechanical", "probability": 0.70 },
    { "axis": "domain", "categoryId": "software", "probability": 0.30 }
  ],
  "experienceRefs": ["mechanical-career-01", "software-career-02"]
}
```

別途、機械系4年とソフト系3年の職歴単位を保存し、それぞれに根拠と分類を持たせる。人物全体のsoftware=0.30だけで「ソフト経験が30%しかない」と解釈しない。

検索例は「同じ分類要素のcategoryIdがsoftware、かつprobabilityが文書側閾値以上」。categoryIdとprobabilityを別々の配列要素で満たすクエリは不正とする。Noul値・語一致による救済は別経路とし、最初から全経路ANDを必須にしない。

全分布を保持するため、閾値の変更にJev再呼出しは不要。分類軸・候補選択肢・質問文を変える場合は再推論対象。モデル・分類体系の異なる分布を無条件に同じ閾値で混在させない。

## 5. 試験パラメーター

以下は探索開始用の仮値であり、正解率や推奨閾値を保証しない。

| パラメーター | 比較例 |
|---|---|
| 文書側Probability閾値 | 0.05 / 0.10 / 0.20 / 0.30 |
| 質問側のカテゴリ展開 | 最上位 / 上位3 / 上位5。other/unknownの扱いは別に記録 |
| 閾値未満の上位カテゴリ救済 | 無 / 上位2を追加。分布が平坦な場合の救済効果を測る |
| Noul閾値 | 0.3 / 0.5 / 0.7。Choice閾値と共用しない |
| ユニーク候補上限N | 20 / 50 / 100 / 権限内全件 |
| 最終提示K | 3 / 5 |
| 根拠の入力量 | 候補別の関連断片数・最大トークン数を固定して比較 |

全組合せをいきなり回さず、一次検索の安価な比較で範囲を絞ってからLLMへ進む。候補上限を適用する前後の集合を両方保存する。上限適用時は経路別の救済枠と人物単位の重複除去を行い、並び順・同点ID順を固定する。

## 6. LLM再順位付けの契約

入力は質問、必要条件、候補ID、関連する職歴/事例の本文、役割、期間、結果、出典ID。Probability/Noulは取得理由の追跡に使い、最初の試験ではLLM入力から外す条件も設ける。分類値へのアンカリングで実経験が過小評価されないかを見る。

出力は候補ID、評価軸ごとの適合判断、最終順位、理由、根拠ID、不足情報。IDは入力集合に限定し、根拠のない新しい経験・資料を追加しない。全件不適合を許容する。失敗・拒否・出力打切りは空結果と区別する。

同じ候補集合で提示順を入れ替え、可能なら複数回評価して順位変動を記録する。分割が必要なら共通基準で個別評価し、分割ごとの「1位」を同じスコアと解釈しない。必要に応じて上位集合を再比較し、呼出回数・トークンを費用に含める。

一次候補に正解がない場合は検索失敗。正解が含まれるのに最終提示から落ちる場合は再順位付け側の失敗。出典の切り詰めで判断材料が落ちた場合はコンテキスト構成の失敗として分ける。

## 7. 指標

| 指標 | 定義 |
|---|---|
| Recall@N | 一次候補N件に含まれる正解数 ÷ その質問の全正解数 |
| HitRate@N | 正解が1件以上一次候補へ入った質問の割合 |
| Precision@K | 最終提示K件中の正解数 ÷ 実際の提示件数。提示0件は別集計 |
| nDCG@K | 人が付けた段階的関連度に基づく順位品質 |
| 最終HitRate@K | 最終提示に正解が1件以上ある質問の割合 |
| Noul救済 | Noulを追加した時だけ入る正解数と、追加される非該当数 |
| 打切り損失 | 統合後には存在したが候補上限の適用で消えた正解数 |
| 費用 | 実測RU、保存/索引量、各モデルのトークン、呼出回数、再試行、処理時間 |

全正解数0の質問はRecall/nDCGの平均から分け、誤推薦率・該当なし判定として報告する。人物と事例を別に集計し、平均だけでなく複数分野・情報不足等のケース別結果を示す。小標本の結果を本番一般精度へ外挿しない。

## 8. 実行順序と判断

1. 既存の日本語分類試験を固定し、正解候補集合を作る。
2. A〜Eの一次検索のみを比較。基礎的な複数職歴の回帰ケースは全件救済を目指す。
3. 調整用データで閾値・N・救済枠を選び、別の確認用データで再評価する。
4. 候補集合を固定し、LLMモデル・プロンプト・根拠量・提示順を比較する。
5. 一連の処理でRecall、最終品質、p50/p95、費用を同時に測る。
6. 不要会話、撤回、AI障害、Queue通知漏れ、Worker再実行を確認する。

暫定の最終品質目安は、正解が存在する20質問中18質問以上で上位5件に正解を1件以上含むこと。これはHitRate@5でありRecall@5ではない。一次Recallの目標値、費用上限、待ち時間の合否はデモ目標と初回実測で確定する。満たせなければ、分類そのもの、検索閾値、上限、根拠量、再順位付けのどこが原因かを分解して次の変更を決める。
