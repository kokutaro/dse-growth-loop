## 第1部　コンセプトと仕組み

### 1. コンセプト

**「誰に聞けばよいか分からない」を減らし、一度の協力を、組織全体の次の解決につなげる。**

組織には、個人の経験、部署の活動、過去の相談という形で知識が存在する。しかし、必要な時に見つからず、同じ調査や試行錯誤が繰り返される。DSE Growth Loopは、それらを課題を起点につなぎ直す。

単なる社員検索やチャットの追加ではない。「課題を見つける → 経験のある人と協力する → 解決に使えた知見を残す → 別の課題で再利用する → 繰り返される困りごとを事業仮説にする」という循環をつくる。

### 2. 目的と守る原則

- 相談先を探す負担を減らす。
- 部署を越えた経験の応用を促す。
- 解決の過程と結果を、後から再利用できる形にする。
- 共通する困りごとを可視化し、新規事業の検討材料をつくる。
- 人の優劣を決める仕組みにはしない。人事評価、社員ランキング、自動配置には使用しない。
- 候補者の提示と参加依頼を分け、協力するかどうかは本人が選ぶ。
- AIの推定、本人の申告、資料に記載された事実を混同しない。本人が訂正できる。
- 「相談が役立った」と「解決した」を分けて記録する。

### 3. 利用者から見た仕組み

| 段階 | 利用者の体験 | 残すもの |
|---|---|---|
| ① 経験を見えるようにする | 職務経歴やスキルシートを登録。抽出された内容を後から確認・訂正 | 経験、得意領域、根拠、確認状態 |
| ② 部署の活動を知る | 週報やトピックスから、どの部署が何に取り組んでいるか分かる | 部署の活動と課題。個人の実績とは分ける |
| ③ 課題から相談先を探す | 困りごとを書くと、参考事例と相談先候補、その理由が提示される | 課題と相談候補。最終的に依頼するのは人 |
| ④ 協力して解決する | 専用チャットで相談。会話に関連する事例が自動で紹介される | 会話、参照した事例、判断の経緯 |
| ⑤ 結果を振り返る | 解決状況と役立ち度を別々に回答。再利用できる要約を確認 | 成果、未解決点、評価、公開用の知見 |
| ⑥ 共通課題を見つける | 複数の相談に共通する困りごとから、事業化候補を検討 | 根拠付きの事業仮説と、次に確かめること |

### 4. 説明用の一例

架空の営業企画課が「案件の引き継ぎで毎回確認漏れが起きる」と相談する。システムは営業経験者だけでなく、製造部門で引き継ぎチェックリストを改善した経験者も候補に挙げる。

協力者が参加すると、会話中に「担当者変更時の確認項目を標準化した事例」が紹介される。相談者は自部署に合う形へ修正し、試した結果と役立ち度を記録する。その知見を再利用できる形で残す。

同種の困りごとが別部署でも繰り返されれば、「部署横断の引き継ぎ支援」という事業仮説が生まれる。ただし、社内で繰り返されたという事実だけで市場需要や事業性が確認されたとは判断しない。

## 第2部　推奨アーキテクチャ

### 5. 結論

**Blobへ原本を保管し、機械抽出・必要な構造化・Jev分類を行う。Choiceの確率分布と補助NoulをCosmos DB for NoSQL Serverlessに保存し、属性索引で広く一次検索する。Foundry上のLLMが取得した候補の根拠を読み、再順位付け・説明を行う。**

Azure AI Search、PostgreSQL、埋め込みモデル、ベクトル検索は初期構成に含めない。コンセプトは変えず、固定費と検証規模に合わせて実現手段を変更する。一次検索は同じ検索条件・データ版・ルールに対して決定論的に実行し、Jevによる条件生成とLLMによる再順位付けはAI処理として区別する。

最初からマイクロサービス群や自律的なマルチエージェントにしない。業務機能をモジュールに分け、Web/APIとWorkerの2プロセスを同じコードベースから動かす。事業化候補抽出は手動を既定とし、定期実行は初期配置しない。

[構成図を開く](diagrams/architecture.html)。図は依存関係の概要であり、全通信・ネットワーク境界を網羅した本番配置図ではない。JevはAzure外のサービス。ブラウザからAI・検索・DBへ直接接続しない。

### 6. 構成・言語の選定案

| 役割 | 初期選定案 | 選定理由・境界 |
|---|---|---|
| 専用Web UI | React / TypeScript / Vite | スキル訂正、候補カード、チャット、事例、事業仮説を一つの画面群で表現。生成した静的ファイルはAPIコンテナから配信 |
| 業務API | C# / ASP.NET Core / .NET 10 LTS | 認可、状態遷移、検索条件、候補集合の統合を管理。大規模な横断トランザクションは前提にしない |
| チャット配送 | ASP.NET Core SignalR | 初期はAPI 1レプリカ。永続メッセージはDB。接続切断時は連番で再取得 |
| 非同期Worker | C# / .NET 10 | 文書取込、AI判定、検索索引更新、チャット支援。APIと業務ルールを共用 |
| 文書抽出 | Open XML SDK | `.docx` / `.xlsx`の文字・構造・出典位置を抽出。画像OCR・旧Office形式は初期対象外 |
| 実行基盤 | Azure Container Apps | APIはHTTP起動の最小0／最大1。取込Workerは実装後にQueue＋MIで起動 |
| 手動実行 | Azure Container Apps Jobs | 現在はseedのみ。事業分析・通知漏れ回復は後続実装でも手動を既定とする |
| 正本・検索用データ | Azure Cosmos DB for NoSQL Serverless | 個人/部署/職歴/事例/会話/評価/確率分布/ジョブをJSON文書で管理。正本と検索用投影は論理的に区別するが同じサービスに置く |
| 原本・抽出成果物 | Azure Blob Storage | バージョン付き原本、抽出テキスト、処理結果を保存。公開URLにしない |
| 検索 | Cosmos DBの属性索引 + アプリ内計算 | 分類ID、Probability、正規化語、経験期間等で検索。質問依存の複合スコアは候補取得後に計算 |
| 非同期通知 | Azure Queue Storage | ジョブID・対象版を通知。完了状態はCosmos DB。手動の回復処理を併用し、DBを常時ポーリングしない |
| AI | Microsoft Foundry + Jev公式API | 各役割をアダプターで分離。モデル交換で業務データ形式を変えない |
| 認証・秘密情報 | Entra ID / Managed Identity / Key Vault | Azure接続は可能な限りManaged Identity。Jev APIキーはKey Vault。UIへ渡さない |
| 運用 | Azure Monitor / Application Insights / OpenTelemetry | 時間、エラー、処理段階、モデル版、トークン量、費用を追跡。本文は通常ログに出さない |
| 開発・配置定義 | Aspire AppHost / Bicep | ローカル依存関係の起動とAzure構成の再現を分ける。バージョンは実装開始時に固定 |

.NET 10は2028年11月までのLTSであり、新規着手時にサポート残期間を確保しやすい。[公式サポート情報](https://learn.microsoft.com/en-us/dotnet/core/releases-and-support)

Python専用サービスは初期には置かない。OCRや複雑な文書解析でPythonライブラリが必要になった場合に限り、抽出Workerを追加する。用途に適した言語を使うことと、最初から多言語化することは分ける。

### 7. Cosmos DB Serverlessを採用する理由

数名・ダミーデータ・断続的利用という条件に対し、常時予約する処理能力を持たずに使えるServerlessを選ぶ。強い業務整合性を全体へ求めるのではなく、本人訂正の競合防止、公開状態、二重投稿防止という必要な箇所に限定する。

| 案 | 長所 | 今回の判断 |
|---|---|---|
| Cosmos DB Serverless + Blob | 属性索引、JSON保存、低頻度利用に適した課金 | 今回の検証構成 |
| Azure Table Storage + Blob | キー中心の単純な検索に適する | 複数属性・閾値の検索用索引を自前管理する負担があるため保留 |
| PostgreSQL + Azure AI Search + Blob | 複雑な結合や広い自由文検索に対応しやすい | 0.1の案。今回の固定費・検索方式には過剰で、初期から外す |
| ベクトル検索の追加 | 分類体系外の言い換え等を補完できる可能性 | 一次検索の失敗分析で必要性が確認された時だけ再検討 |

Cosmos DBの等価・配列要素・数値範囲の索引を使うため、日本語のネイティブ全文検索対応は今回の採用条件ではない。正規化した検索語と分類IDを登録時に生成する。本文の任意部分一致を主経路にしない。[索引仕様](https://learn.microsoft.com/en-us/azure/cosmos-db/index-overview)

Serverlessは消費RUと保存量に基づく課金で単一リージョン。NoSQLなら常に安いという意味ではなく、検索RU、索引更新、背景処理、ログを含めて測る。[Serverless仕様](https://learn.microsoft.com/en-us/azure/cosmos-db/serverless)

### 8. AIの役割とモデル候補

| 役割 | 初期候補 | 入力 → 出力 |
|---|---|---|
| 文書の構造化 | Foundry `gpt-5.6-luna` | 出典位置付き抽出テキスト → 検証可能なJSON |
| 業種・職種・スキル分類 | Jev `jev-1.13.0` | 必要な事実と分類基準 → 選択肢・確率分布 |
| 経験有無の補助判定 | 同上、Noul | 職歴・事例の根拠 → 「その経験があるか」のyes確率 |
| チャット支援の開始判断 | 同上、Noul等 | 直近会話の必要部分 → 検索が有用かという判断 |
| 検索後の再順位付け・説明 | Foundry `gpt-5.6-luna` | 課題と広く取得した職歴・事例の根拠 → 候補ID、順位、理由、注意点 |
| 要約・複雑な事業仮説整理 | まず同一モデル。評価不足なら`gpt-5.6-terra`を比較 | 根拠と計算済み集計 → 要約・仮説 |
| 品質比較の上限候補 | `gpt-6-astra` | 評価用のみ。全処理への常用を前提にしない |

Foundryの候補モデルは比較開始点で、地域・クォータ・契約により利用可否が異なる。再順位付けの品質・速度・費用は今後測定する。埋め込みモデルのデプロイは不要。[Foundryモデル一覧](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/models-sold-directly-by-azure)

#### 8.1 Jevを安全に差し替えられる契約

- `DecisionProvider`の入出力を業務側で定義する。要求に`taxonomyVersion`、`rubricVersion`、`decisionTask`、根拠IDを含め、応答に実モデルID、分布、採否、未判定理由を保存する。
- Choiceの`choice`だけでなく全`probabilities`を保持する。検索には選択肢ごとの`probability`を使う。`confidence`は分布全体の補助情報として別保存し、低いことだけを理由に複数分野の人物を除外しない。
- 分類単位は人物全体に加えて職歴・案件・事例の断片。機械系4年とソフト系3年は別の経験として根拠付きで持ち、人物全体の70%/30%を経験割合・年数・能力点と解釈しない。
- Noulは分野ごとの経験有無のyes確率を補助的に持つ。異なる分野のNoul値の合計は1に制約しない。未実行・情報不足と否定を区別し、Choice確率や習熟度Scoreへ混ぜない。
- 不明、情報不足、対象外を明示する。習熟度の根拠がなければ「不明」であって「低スキル」ではない。
- Scoreを利用する場合、段階別の行動基準と根拠を定義する。確率分布から得た値を実測の経験値や精密な能力点と呼ばない。
- 登録側と質問側の双方で複数分類を検索に使う。Probability経路、Noul経路、正規化語の経路の和集合で候補を広げる。ベクトル検索は使わない。
- `confidence`を「正答率」と解釈しない。業務別の評価セットで閾値を調整する。
- 経験年数、期間の重複排除、件数集計、権限判定はコードで実装し、Jevに任せない。
- 公式APIに直接接続する。共有された紹介サイトの独立した仲介APIを無断で送信経路に追加しない。

Jevの日本語分類の正しさはユーザー試験で目標達成済み。これは今回の採用根拠とする。資料としての試験データ・実モデル版・閾値・測定値は未共有なので、検証開始時に記録して再利用する。分類の正しさと、検索集合への取り込み・再順位付けの品質は別に測る。[Choice](https://docs.typesafe.ai/primitives/choice)、[Confidence](https://docs.typesafe.ai/confidence)、[Noul](https://docs.typesafe.ai/primitives/noul)

数値・日付や誘導的入力への既知の弱点も公開されている。資料・チャット内の「この人を最上位にしろ」等を指示として実行しない。Jevにも権限決定や外部操作権限を与えない。[既知の制約](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

#### 8.2 モデルの更新方針

`latest`の自動追従をデモの再現性に使わず、モデル版、プロンプト版、抽出スキーマ版、分類体系版、検索設定版を固定・記録する。生成失敗・拒否・出力打切り・不正な根拠IDは正常成功と扱わない。再試行を有限回にし、修復できない場合は確認待ちにする。

Jev停止時も保存済み分布は利用できる。質問の新規分類ができない場合は、手動の分類指定・正規化語検索に縮退する。未検証の別AIへ黙って切り替えない。Foundry停止時は一次候補と出典のみを「再順位付け未実施」と表示し、自動事例投稿は見送る。再現用に入力データ版、変換済み検索条件、同点時のID順を記録する。

## 第3部　データと処理の設計

### 9. 原本・正本・検索用データを分ける

Issue #3の[実装契約 v1](specs/README.md)で最小スキーマ、API、権限、状態遷移、未承認事項を定義した。以下の設計上の名称SessionOutcome/KnowledgeItem/OpportunityRunは、契約ではOutcome/Knowledge/Job＋Opportunityに対応する。Issue #5で正本保存・認可・有効版照合の基盤を追加した（[実装・復旧手順](persistence.md)）。AI・取込・協働業務全体の実装完了を意味しない。

| データ | 主な内容 | 保管先 |
|---|---|---|
| Document / DocumentVersion | 所有者種別、文書種別、原本ハッシュ、Blobキー、版、処理状態、閲覧範囲 | Cosmos DB。ファイル本体はBlob |
| EvidenceSpan | 文書版、シート/セル範囲、段落/表位置、引用テキスト | Cosmos DB + 大きな抽出結果はBlob |
| Person / Experience / SkillEvidence | 架空社員、職歴・案件単位の役割、期間、根拠、確認状態 | Cosmos DB |
| ClassificationResult | 単位ID、分類軸、全Probability、Choice、Confidence、モデル/分類基準の版 | Cosmos DB。大きな生応答はBlobへ退避可 |
| ExperienceSignal | Noulの質問ID、yesProbability、根拠、判定状態、版 | Cosmos DB。未判定をfalse/0へ変換しない |
| DepartmentActivity | 部署、活動、対象期間、関係する課題、根拠 | Cosmos DB。所属者全員にスキルを付与しない |
| Challenge / Participation | 課題、公開範囲、依頼、参加承諾、辞退、対応可能状態 | Cosmos DB |
| Session / Message | 参加者、会話連番、発言者種別、メッセージ、AI投稿の出典 | Cosmos DB |
| SessionOutcome / Feedback | 解決状態、役立ち度、任意コメント、評価者、評価時刻 | Cosmos DB |
| KnowledgeItem / Approval | 公開用要約の版、元セッション、根拠、公開先、確認者、公開状態 | Cosmos DB |
| OpportunityRun / Hypothesis | 分析対象時点、集計、グループ、根拠課題、仮説、検討状態 | Cosmos DB |
| Job / AiRun / RetrievalRun | 対象版、再試行、実モデル、使用量、候補集合、脱落段階、検索ルール版 | Cosmos DB。Queueには小さな通知のみ |
| SearchUnit | 職歴・事例単位の検索投影、分類Probability、Noul、検索語、ACL、版 | Cosmos DB。元の事実・全分布から再生成可能 |

日付不明・経験期間不明・評価なしはNULLや明示的なunknownとし、0年・0点に置き換えない。経験期間が重なる複数案件を単純加算しない。本人訂正を再取込のAI出力で上書きせず、競合は確認対象にする。

#### 9.1 スキルをすぐ使うための状態設計

根拠検証済みの抽出結果は`ai_unconfirmed`として直ちに検索対象にする。UIには「AI抽出・本人未確認」を表示し、出典と訂正ボタンを付ける。本人が変更すれば`self_corrected`、確認すれば`self_confirmed`とする。本人確認は客観的な資格認定とは区別する。

構造化できない項目や存在しない根拠を持つ主張は検索に出さない。「本人確認待ちにしない」という要望は、壊れたデータや無根拠の推定も公開するという意味ではない。

#### 9.2 Cosmos DBの検索用文書・索引

この節には将来拡張の属性候補も含む。最初の書込契約の必須フィールド・型は[JSON Schema](specs/contracts.schema.json)を正本とし、`sourceVersion`、`activeVersion`、`projectionVersion`、`accessVersion`で文書・投影・公開版を区別する。現行fixtureは別のLegacySearchUnit契約で互換性を検証する。

検索単位は職歴・案件・事例断片とする。人物全体の分類は補助とし、人物単位の候補集合は各職歴のヒットの和集合から作る。

- 共通：`id`, `entityId`, `entityType`, `unitId`, `tenantId`, `documentVersion`, `projectionVersion`, `scopeIds`, `status`, `title`, `sourceRefs`, `updatedAt`。
- Choice投影：`classifications[] = { axis, categoryId, probability, rank, classificationRunId }`。`axis + categoryId + probability`は同じ配列要素内で照合する。別の分類のProbabilityと誤って組み合わせない。
- Noul投影：`experienceSignals[] = { signalId, yesProbability, evidenceState, sourceRefs, decisionVersion }`。Choiceと別の経路で検索する。
- その他：`normalizedTerms[]`, `skillIds[]`, `experienceMonths`, `lastUsedAt`, `confirmationState`, `availability`, `knowledgeType`, `publicationVersion`, `outcome`。全文・引用・生応答は必要な時だけ読む。
- 全Probabilityを正本に保持し、検索用投影にも初期は全分類の数値を残す。検索時の閾値を変えるだけなら再推論不要。将来保存量を絞る場合も全分布は保管し、再投影で回復可能にする。
- `confidence`は分類実行単位の診断情報として保存し、候補採否の共通ゲートにしない。Probabilityも実測の正答率・経験割合・能力点とは扱わない。
- 検索語は登録時と質問時に同じ正規化を適用する。分類ID辞書、同義語、略語、英字表記等を版管理し、汎用本文部分一致に依存しない。
- 索引対象は検索する分類・数値・語・版・状態等へ限定。長文本文や生AI応答は不要なら除外する。複数フィールドの並べ替えに必要な複合索引は実クエリを測って定義する。

初期コンテナ案は`catalog`（人物・職歴・文書・公開知識・SearchUnit、partition key `/tenantId`）と`conversations`（会話・評価・セッション処理、partition key `/sessionId`）。ジョブは原則として対象と同じコンテナ・論理パーティションに置く。テナント内検索を局所化する設計であり、大規模化時はパーティション集中・容量を再設計する。会話のテナント所属はサーバー側で検証し、sessionIdを知っているだけでは読めない。

原本、正本、検索投影を区別するが、サービスを三重化しない。検索投影の更新遅延は許容し、AI入力前に正本の有効版・公開状態を照合する。更新直後の確認にはセッショントークンの引継ぎ等を含めた読み取り整合性を検証する。

### 10. データ蓄積の流れ

1. 利用者が種類と対象者/部署を指定してアップロード。サーバーが拡張子・実形式・サイズ・圧縮展開上限を検査する。
2. Blobへ原本を保存し、文書版・ハッシュ・取込ジョブを登録。同一ハッシュでも所有者や公開範囲が違う場合は同一文書扱いにしない。
3. Workerが機械抽出。Excelは見出し、シート名、セル位置、結合セル、数値の単位を残す。Wordは見出し、段落、表の関係を残す。マクロ・外部参照は実行しない。
4. 固定書式から取れる日付・識別子は機械的に構造化する。自由記述の解釈が必要な箇所だけFoundryへ渡し、JSON Schemaに沿って職歴・案件・事例単位へ構造化する。命令と資料を区別する。
5. 構造・ID・日付・引用元・根拠に一致する記載の有無を検証。曖昧な値は不明として保持する。
6. Jevで単位ごとのChoice確率分布と補助Noulを取得。人の技能と部署の活動を別エンティティへ保存し、日付計算はコードで行う。
7. Cosmos DBへ根拠・全分布・処理版を保存。対象と同じ論理パーティション内で検索投影更新ジョブを確定し、Queueへ通知する。DBとQueueは一括トランザクションではないため通知失敗を回復する。
8. SearchUnitを生成する。旧/新版の混在は親の有効版との照合で除外し、新版の投影が揃ってから切り替える。埋め込みは生成しない。再投影で本人訂正を消さない。
9. UIに取込状態、件数、未確認項目を表示。AI抽出完了後、索引反映を経て検索対象となる。反映中を「即時に検索済み」と表示しない。

Open XML SDKを抽出の基礎とする。初期デモでは暗号化ファイル、旧`.doc`/`.xls`、画像だけの資料を保留・拒否し、対応外と表示する。[Open XML SDK](https://learn.microsoft.com/en-us/office/open-xml/about-the-open-xml-sdk)

### 11. 候補者・事例検索

1. 課題を検索語・必要条件へ整理し、質問側でもChoiceの全分布を得る。同じ分類体系の複数候補へ展開する。
2. 公開範囲・削除状態・検索参加可否を必須条件にする。分類の低確率は「経験なし」とはみなさない。必須資格等は明示された場合だけ強い条件にし、不明は確認が必要と示す。
3. 一次検索の経路A：質問側で選んだ複数カテゴリについて、文書側Probabilityが閾値以上の単位をCosmos DBの索引で検索する。閾値と上位カテゴリ救済数は分類軸ごとに版管理する。
4. 経路B：質問で必要な経験に対応するNoul値が閾値以上の単位を検索する。経路C：正規化語・スキルIDが一致する単位を検索する。A/B/Cは原則ORで統合し、複数条件を全部ANDにして取りこぼしを増やさない。
5. 同じ人物・事例をまとめつつ、どの職歴がヒットしたかを保持する。分類確率を職歴間で平均して少数分野を薄めない。一次順位の仮ルールは一致カテゴリ数、該当分野の最大Probability、語一致数、安定ID順とし、Noulによる救済候補にも枠を確保する。これは適合確率の推定式ではない。
6. 統合前の件数、重複除去後、上限適用後を記録する。LLMへ渡す候補数Nを20/50/100等で比較し、少数データでは全件も比較する。上限は最終順位とは別の制約であり、打切りによる取りこぼしを測る。
7. 正本で権限・公開状態・版を照合し、各候補の関連職歴/事例本文、担当役割、期間、結果、出典を取得する。分類ラベルやProbabilityだけをLLMへ渡して再評価したことにしない。
8. FoundryのLLMが同じ評価基準で適合性を再評価・再順位付けし、理由・不足点・根拠IDを返す。Probabilityは検索経路の診断情報とし、最終順位を固定する能力点にしない。モデルに渡す場合はアンカリングの有無を比較する。
9. 出力IDが候補集合に含まれるか、重複・不正な根拠がないかを検証。該当なしを許容し、初期提示は3〜5件。相談先への依頼・参加は人が決める。

数値の保存済み項目での絞り込みと、質問ごとに変わる総合スコアは分ける。後者はアプリで計算し、任意の計算式をDB索引だけで高速に並べ替えられるとは仮定しない。一次検索はデータ版・条件・ルールが同じなら再現可能だが、LLM再順位付けを含む全工程は完全な決定論ではない。

大量の候補を分割してLLM評価する際は共通の採点基準と根拠付き個別評価を用い、分割内の順位番号をそのまま全体順位にしない。候補の提示順による変動や、分割後に必要な全体比較を検証する。詳細は[検索検証計画](retrieval-validation-plan.md)。

### 12. チャットへのAI自動投稿

チャットメッセージは、AI処理を待たずにDBへ保存して相手へ届ける。同じセッションの論理パーティション内で支援ジョブも登録し、Queueへ通知する。AIが失敗しても人同士の会話は続く。DB障害時は未保存メッセージを保存済みと表示しない。

**処理順序：人の投稿 → 少しまとめて判断 → 関連事例検索 → 適合性確認 → 根拠付きの短い投稿。**

- AI自身の投稿は新しい検索のトリガーにしない。無限の自己応答を防ぐ。
- 仮設定：最後の人の発言から3秒まとめ、直近8メッセージ程度と確認済みの論点だけを渡す。長さにも上限を設ける。
- Jevは「新しい問題/制約が示されたか」「参照事例が有用そうか」を判定する。発火後は11節の複数Probability・補助Noul・語一致による候補収集とFoundry再順位付けを再利用する。
- 自動投稿は公開済みの事例を対象とする。投稿先メンバー全員が閲覧できるかを確認する。個人用の検索権限をそのまま共有チャットへ持ち込まない。
- 仮設定：60秒のクールダウン、1回1件、1セッション最大5件。同じ`sourceId + sourceVersion + sessionId`は原則再掲しない。論点の変化と明示的な再要求は別途扱う。
- 関連性が低い、根拠なし、Jev判定不能、予算上限、会話が終了済みの場合は投稿しない。沈黙が正常な結果になり得る。
- 生成中に進んだ会話を投稿前に再確認する。参加者・公開範囲・会話版が変わった場合は再判定または破棄する。
- 投稿の形式は「参考事例／今回との共通点／適用上の違い／出典」。断定的な解決命令にしない。
- 利用者が自動支援を停止・再開でき、投稿へ「役立つ／不要」を返せる。セッション全体の評価とは分ける。

人への実名開示や参加依頼をAI事例投稿に便乗して実行しない。自動投稿の権限は知識の紹介までとし、ファイル編集・外部送信・任意ツールの実行権限を与えない。

### 13. 解決・評価・知識化

解決状態は`open / partially_resolved / resolved / unresolved_closed`。役立ち度は5段階を初期案とし、未回答を許可する。評価はセッションの有用性であり、協力者の人事評価には流用しない。

会話を閉じたら、Foundryが「課題／前提／試したこと／結果／再利用条件／未解決点」を下書きする。推測と確認された結果を分け、元メッセージや参照事例への根拠を残す。

暫定公開フローは`draft → review_requested → published`。参加者が公開範囲と要約版を確認して公開する案。確認中に編集されたら再確認し、公開済み版を変更した場合も新しい版として扱う。AIによるチャットへの自動投稿を許可したことを、全会話の自動公開許可とは解釈しない。

公開撤回はまず正本側で即時ブロックし、索引・キャッシュ・引用表示を追従更新する。物理削除の完了まで古い検索結果が残っても、最新認可でAI入力・画面表示を遮断する。

### 14. 事業化候補の抽出

対象は再利用・分析を許可した課題要約と知識であり、私的な会話全文を無条件で巡回しない。解決済み・高評価の事例だけでなく、公開可能な未解決課題も需要の兆候として分けて扱う。

1. 分析対象の時点・対象集合・設定版を固定する。
2. 同じ案件の週報反復や同一セッション由来の重複を除き、独立した課題ID単位へ整理する。
3. 分類Probability・正規化語の重なりで関連課題候補を広く取得する。必要な経験等のNoulも補助利用し、Foundryが根拠から共通課題を確認する。埋め込み・大規模クラスタリング基盤は置かない。最大分類が違っても共通の副分類を持つ課題を含める。
4. 件数、独立部署数、再発、未解決比率、申告された工数/負担をコードで集計する。資料枚数を需要件数と呼ばない。
5. 集計と根拠をFoundryへ渡し「対象者／共通の困りごと／既存の対処／仮の提供価値／反証／次の顧客確認」を作る。
6. 人が`候補 / 調査中 / 保留 / 却下`を決める。自動で事業化決定しない。

仮の抽出条件は「独立した課題が3件以上、かつ複数部署」。デモデータ向けの説明用条件であり市場性の閾値ではない。小集団は特定につながるため、実データへ移る際は集計公開の最小集団サイズを別途定める。市場規模・売上・ROIを社内の件数だけから生成しない。

初期検証では「今すぐ分析」の手動実行だけを実装する。日次スケジュールは配置しない。`runId`/対象版管理・重複抑制を使用する。[Jobsの公式仕様](https://learn.microsoft.com/ja-jp/azure/container-apps/jobs)

### 15. 非同期処理と整合性

初期はCosmos DBに永続ジョブを置き、Azure Queue StorageをWorkerへの通知に用いる。検索・会話の正本とジョブは可能な範囲で同じコンテナ・論理パーティションに配置する。DBの常時巡回は避ける。更新競合はETag、同一パーティションの複数更新はTransactional Batch等で保護する。コンテナ横断の一括更新は前提にしない。[整合性・競合制御](https://learn.microsoft.com/en-us/azure/cosmos-db/database-transactions-optimistic-concurrency)、[Queue Storage](https://learn.microsoft.com/en-us/azure/storage/queues/storage-queues-introduction)

- ジョブ：`jobId`, `type`, `aggregateId`, `aggregateVersion`, `payloadVersion`, `dedupKey`, `status`, `attempt`, `availableAt`, `leaseUntil`, `lastErrorCode`。
- DB保存後にQueue通知する。通知失敗・保存後のプロセス停止は、明示的再実行と手動の未完了ジョブ照合で回復する。開発時は自動巡回せず、手動回復までの通知遅延を許容する。常時即時配送のSLAは設けない。
- 処理：at-least-once。WorkerはETagによるリース獲得と期限更新を実装し、Queueの不可視期間も処理時間に合わせて延長する。完了済みの再通知は読み捨てる。
- AIの重複呼出し課金まで完全に防げるとは保証しない。保存・投稿には一意キーを使い、重複表示を防ぐ。
- 初期再試行案：最大3回、指数バックオフと揺らぎ、APIのRetry-Afterを尊重。認証・スキーマエラーは無条件で再試行しない。
- 上限超過は`failed`にして管理画面から再実行。旧版イベントは最新の業務状態と比較して破棄する。
- 複数のSearchUnitは途中で部分更新になり得る。親の有効版・投影完了状態との照合で混在を除外し、手動の照合で未反映を回復する。
- 原本アップロードとDB確定も同一トランザクションではない。中断された一時Blobを識別し、期限後に回収できるようにする。

Service Bus、Redis、Azure SignalR Serviceは見送る。Queueの取得・スケール監視にも費用があるため、空キュー時の間隔を延ばし、デモ時間外のWorker稼働を制御する。QueueとDBを跨ぐexactly-onceは主張しない。複数APIレプリカが必要になった際はSignalRの配送構成を見直す。

## 第4部　安全性・実装・評価

### 16. ダミーデモでも維持する境界

- UIに「デモ・架空データ」と表示。実際の職務経歴や社内週報を使わず、マスキングした実資料を自動的にダミーと呼ばない。
- 認証された少数ユーザーのみ。ブラウザにCosmos DB/Storageの資格情報やJevキーを配らない。
- 原本はサーバー経由の認可取得、または必要最小限・短時間の署名URL。匿名公開しない。
- ユーザー入力、取得文書、チャット中の命令は信頼しない。モデルが返す権限・URL・候補ID・数値を検証する。
- 実際のログイン情報や接続情報はダミーではない。AI送信対象から除外する。
- 管理ログには本文を記録せず、ID・版・処理時間・エラー・使用量を残す。デバッグ本文記録は明示的なダミー専用設定に限定。
- 検索前の絞り込み、AIへ渡す前、共有投稿の確定前に公開状態を確認する。
- 事業分析は専用権限を持つ処理として対象を限定する。全データ閲覧権限と一般利用者への集計公開権限を混同しない。

実データに変更する場合は別レビューを必須にする。必要項目は、本人への説明、利用目的、保存期限、公開/訂正/削除の運用、委託先契約、越境処理、ログの扱い、ネットワーク制御、復元時の削除反映、運用責任者である。現在のダミー送信許可を実データの許可に引き継がない。

Jevの顧客データ非学習方針とデータ保持なしは別条件である。Enterprise向けZDRは別途確認事項であり、通常契約を自動的にZDRとは扱わない。[公式Legal](https://docs.typesafe.ai/legal)

### 17. デモUIの画面案

1. **ホーム/課題登録**：困りごと、公開先、参考事例、相談候補への導線。
2. **データ登録/取込状況**：ファイル、文書種別、対象者/部署、成功/保留/失敗、出典確認。
3. **プロフィール**：経験・スキル、未確認表示、根拠、本人訂正、参加可否。
4. **検索結果**：候補者と事例、適合理由、違い、根拠、依頼/参加承諾。
5. **チャット**：人の会話、AI事例投稿、出典、不要フィードバック、自動支援の停止。
6. **解決/知識化**：解決状態、役立ち度、要約編集、公開範囲、確認状態。
7. **事業化候補**：共通課題、独立件数、部署数、根拠、仮説、反証、次の確認。
8. **管理/デモ操作**：取込再実行、分析の手動実行、AI障害表示、利用量、ダミーシナリオの切替。

### 18. 推奨する実装順序

| 段階 | 実装する縦の流れ | 完了条件 |
|---|---|---|
| 0 | 既存の分類試験を記録・検索用の正解集合を用意 | ユーザー検証済みの分類を基礎に、複数分野・情報不足・難しい非該当例を追加 |
| 1 | ファイル → 構造化 → 根拠確認 → スキル訂正 | 出典を開ける。訂正が再取込で失われない |
| 2 | 課題 → Probability/Noul/語一致検索 → Foundry再順位付け → 参加 | 一次検索Recallと最終順位を分離して測る。異業種・副分野も拾う |
| 3 | 会話 → AI事例自動投稿 | 無関係な会話では投稿しない。重複・連投・自己応答を防ぐ |
| 4 | 解決状態/評価 → 公開用知識 → 次の検索 | チャット全文公開をせず、承認済み知識が再利用される |
| 5 | 共通課題集計 → 事業仮説 → 人の検討 | 元課題へ追跡でき、同じ週報の重複が水増しされない |

アプリ実装前に、検証用Azure環境でFoundryモデル・Cosmos DB Serverless・Queueを使えるか、既存のJev試験環境をどう接続するかを確認する。ユーザー環境でのJev分類試験と、本リポジトリで未実施の統合試験を区別する。固定デモ結果と実際のAI処理結果も明確に区別して実演する。

### 19. 評価計画

分類品質はユーザー試験で目標達成済み。それ以外の数値は未実測の暫定受入目安で、業務データに対する品質保証ではない。次の主目的は「広く拾えるか」と「拾った中から適切に絞れるか」の分離検証。実験条件、指標の定義、比較構成、出力形式は[検索検証計画](retrieval-validation-plan.md)で定める。

| 観点 | 測り方 | 初期の受入目安 |
|---|---|---|
| 構造化 | 正解セットに対する主要項目と根拠の一致 | 主要項目90%以上、表示する主張に有効な根拠ID100% |
| 分類 | 既存試験を回帰テスト化 | ユーザー検証済み。測定値・モデル版は受領後に記録し、変更時の劣化を確認 |
| 一次検索 | 候補数NでのRecall@N、HitRate@N、経路別救済件数 | 主評価。Top-1のみとの比較で改善を測る。複数分野の指定回帰例をすべて拾う |
| 再順位付け | Precision@5、nDCG@5、HitRate@5、正解候補を落とした割合 | 20課題中18件以上で上位5件に正解1件以上を暫定目安。これはRecallではなくHitRate |
| 自動投稿 | 有用な場面と不要な場面の両方を判定 | 不要会話20例で誤投稿2例以下、同一イベント重複投稿0 |
| 根拠性 | 理由・要約を出典と照合 | 架空の候補・資料・根拠IDの採用0 |
| 権限制御 | 別スコープ、撤回直後、参加者変更、遅延索引 | 禁止資料のAI入力・表示・投稿0 |
| 耐障害 | Jev/Foundry停止、Queue通知失敗、Worker再起動 | DB正常時は会話保存を継続。再実行で二重投稿しない。DB停止時は未保存を明示 |
| 事業仮説 | 課題重複と部署別件数を照合 | 集計は正解と一致。根拠なしの市場数値を出さない |
| 待ち時間 | ウォーム状態で段階別p50/p95を測る | 検索説明10秒以内、自動事例投稿は発火後15秒以内を目標 |
| 費用 | 検索RU、書込RU、LLM入出力、候補数、補助Noul費、空キュー監視費 | 候補数20/50/100と全件を比較。費用上限決定後に合否基準を設定 |

Top-1のみ、Probability複数候補、職歴単位、補助Noul追加、正規化語追加を段階比較する。一次候補集合を固定した再順位付け試験も行い、取りこぼしが索引検索で起きたのかLLMで起きたのかを区別する。Noul有無の費用と救済率を測り、補助指標の効果を確認する。LLMが一次集合にない候補を復活させた扱いにしない。

### 20. 費用と運用

総費用は「Cosmos DBのRU・保存量 + Container Apps稼働 + Blob/Queue/通信/ログ + Foundryの構造化・再順位付け・生成 + Jevの分類・補助Noul + 開発運用時間」で見積もる。AI Search、PostgreSQL、埋め込み処理の費用は含めない。予算・稼働時間が未確定のため、月額や納期を確約しない。

- APIは最小0／最大1のHTTP起動。待機Workerは配置せず、取込実装後はQueue＋MIで0台から起動する。定期ウォームアップは行わない。[ADR-11と費用ガード](development-cost-controls.md)を参照。
- Cosmos DB Serverlessは予約RU/sの固定費を持たないが、保存量・索引・読み書きの課金があり、基盤全体が無料になるわけではない。広すぎる検索、不要な索引、クロスパーティション読取り、背景照合を測る。
- 取込は原本ハッシュと処理版で再利用し、チャットは差分と短い論点に限定する。
- LLM入力件数、最大トークン、同時実行数、再試行、投稿回数に上限を設定する。
- 一次候補を増やすとLLM再順位付け費用も増える。上限を下げる場合はRecallへの影響を記録する。コスト都合の打切りを「適合候補なし」と表示しない。
- Azure Budget等の通知だけを強制停止機構とみなさない。アプリ側にも日次使用量の上限とAI停止設定を設ける。
- 永続キャッシュや追加モデルは、効果を測ってから導入する。
- 稼働時間、ログ保存、バックアップ保存、モデル課金条件を実装前に見積書へ固定する。

### 21. 今回やらないこと

本番SLA、実データ処理、Teams/SharePoint連携、全社員展開、自動人事評価、全社的な匿名保証、モデルの独自学習、大規模データレイク、自律マルチエージェント、全マイクロサービス化は対象外。これらを追加する際は目的・費用・安全性を再レビューする。

AI Search、PostgreSQL、埋め込み・ベクトル検索も今回の初期構成には入れない。分類体系と正規化語で救えない検索失敗が確認された場合に限り、追加手段を評価する。
