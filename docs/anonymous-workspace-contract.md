# Anonymous workspace server contract

`/api/v1/workspace` uses the existing authenticated `ActorAccess`/IdentityResolver and current server repository in both Demo and Azure modes. DTO allowlists are in `Dse.Domain/AnonymousWorkspace.cs`; server adapters and endpoints are `AnonymousWorkspaceService.cs`, `AnonymousWorkspaceKnowledge.cs`, and `AnonymousWorkspaceEndpoints.cs`. Register `AnonymousWorkspaceService` with the same repository, SourceGuard, AccessFence, ConversationService, KnowledgeService, IdentityResolver, configuration and clock as the existing app, then call `MapAnonymousWorkspace` on the authenticated v1 group.

## Capabilities and legacy isolation

`contractVersion=anonymous-workspace-v1`, `available`, `structuredIdentifiersRemoved`, `roomLocalAliases`, and `opaqueOperationIds` are true. `freeTextAnonymized=false`. `legacyApiIsolation=operator-or-development` is advertised only when `Workspace:LegacyApisRestricted=true`; otherwise it is `not-enforced`. This flag must be set only alongside enforced legacy API restrictions by the hosting app. Employee UI must require this isolation value and use only the workspace routes. The server service alone cannot isolate old routes, SignalR, jobs, person search or arbitrary record APIs. Legacy access must be limited to operators in production; development fixture tools remain outside the employee privacy boundary. Profile/document access must remain self-only. Processing mode `fixture` is not Azure or live AI evidence.

Structured employee/principal/tenant/participant/owner/source/scope/evaluator IDs and raw original citations are never fields in workspace responses. Public identifiers (`awc-`, `awr-`, `awi-`, `awm-`, `awk-`) and aliases (`awa-`) are random values persisted in private idempotency records, not hashes of a person or public IDs reused as internal session IDs. Alias IDs are independent for each room. Mapping indexes contain internal hashes only in storage and are not API resources. ETags are concurrency validators. Pagination is encrypted, principal/tenant/filter-bound and expires using the existing PageTokens implementation; raw repository continuation tokens are not returned.

## Read/write behavior

Challenge/invitation context (title and summary) is available to the owner and invited recipient before acceptance. Private room, chat, knowledge and identity-consent data require current membership and intersecting tenant/scope authorization; invitation or guessed opaque ID alone does not authorize access. Accept joins immediately without extra requester approval. Leave revokes room access. Every read re-resolves current authority; response building and serialization stay within the tenant durable AccessFence. Private room responses also hold ConversationLocks throughout serialization. New mutations acquire that fence before the existing conversation locks; Knowledge/participation services which already own the fence are called without a nested fence and their responses are separately revalidated before serialization. An interrupted or ambiguous consumer preserves the existing fail-closed fence/recovery behavior.

Declined/left lost acknowledgements can replay only the existing conversation receipt: tenant, actor, operation/key hash, exact input+ETag fingerprint, source participation and current recipient binding/scope are rechecked under fence and room lock. Replay returns status only and never restores room body access. A changed body/key is rejected rather than issuing a second departure.

Writes retain the original service's `Idempotency-Key` and `If-Match` contracts, with input allowlists rejecting unknown structured fields. Message `clientMessageId` must be a canonical UUID, and is returned only to its author for pending-send recovery; other participants receive null. Saved message IDs are stable opaque IDs across retries. The durable internal message outbox contains no body/name; employee hints/polling carry no body/name or raw subscription IDs. Internal worker messages may contain internal routing IDs and are not employee-visible. Chat read polling works without the old SignalR hub. After commit, the endpoint triggers the existing durable outbox delivery with a two-second limit and private routing IDs; failures are swallowed so the saved message remains saved. Saving a message is not evidence that AI processing or transport delivery completed.

Invitation candidates are derived from the challenge text through existing retrieval, SourceGuard and current profile availability. `awt-` tokens expire after ten minutes, are bound to the issuing owner and challenge version and cannot be replaced with a person ID. Invite revalidates the selected current source and freshly resolved target binding/scope/availability before creating the participation. Primary profile owner must exactly match the current binding principal. Existing alias bindings are also reread and fail closed after rebinding; old alias mappings never authorize the new principal. The internal identity-consent-only resolver preserves already stored peer aliases when a peer becomes ineligible so disclosure can permanently clear all old grants and report unavailable; it still rechecks the caller’s current principal, scopes and membership, never returns room/chat/knowledge body, and never creates a missing alias without the strict validation.

Known literal participant IDs/principal IDs/profile display names and obvious email/UUID shapes are rejected in new free-input requests. Existing unsafe text is replaced with a neutral display notice; unsafe published-case content fails closed. This is a bounded defense, not complete text anonymization: unknown names, indirect identification, context, pasted documents and model inventions may still identify someone. Explicit real-name disclosure is a separate consent endpoint; case-publication and analysis consent remain separate.

## Knowledge adapter

All draft/read/edit/review/consent/approve/withdraw/outcome/feedback/recovery actions go through the existing authoritative KnowledgeService. Participant/evaluator/consent keys are room aliases; self is labeled `あなた`. Scope references (`aws-`) and evidence references (`awe-`) are room-local random tokens resolved back to existing IDs only after current membership and allowed-source checks. Other-room tokens or raw IDs are rejected. Nested section objects allow only field/text/basis/evidenceIds. Numeric metadata validation remains strict. Editing increments the source version and resets publication/analysis consents through the existing service, while changed/withdrawn catalog sources fail SourceGuard validation.

`analysisMetadata.departmentId` is null or an `awd-` token for a previously stored department value; raw department IDs cannot be submitted or returned. The existing IdentityResolver does not provide an authoritative self-department catalogue, so anonymous UI cannot invent or infer a department from a scope or profile. Introducing new department metadata requires an independently authorized category/token provider; this remains an explicit limitation for distinct-department analysis.

Public case search/detail requires a current source projection AND approved conversations authority (`knowledge-v1`, current membership/version, all participant publication consent). Seed catalogue entries without that authority are excluded. Published DTO contains only opaque case ID, title, approved sections, derived summary, version and processing mode. It has no raw evidence references, case participant IDs, raw metadata, draft or conversation body. Withdrawal/edit/membership changes invalidate former public IDs via SourceGuard and the authority check.

## Evidence and pending work

`AnonymousWorkspaceTests` exercises in-memory repositories under both Demo and Azure-mode IdentityResolver bindings, invite-before-join rejection, immediate join/leave, tenant/scope isolation, unlinkable aliases, raw-ID/unknown-field rejection, message idempotency/self UUID, current source availability, response-consumer fence+room lock, knowledge token translation, edit consent invalidation and former-case denial. These are local server regression tests with fixture AI, not Azure authentication, transport, Cosmos RU, production concurrency or live model-quality certification. Root integration owns legacy restrictions, DI, browser E2E and actual transport verification. No deployment, paid resource startup or live AI call is part of this implementation.

## Local fixture preservation

Demo seeds are not an automatic migration. Existing local records may retain the earlier demo profile owner/principal mismatch; binding checks now reject those records instead of changing user corrections. The AppHost accepts `Data__LocalPath` for an explicitly chosen isolated fixture store while keeping its previous default. For this browser review use a new path, for example `Data__LocalPath="$PWD/.artifacts/workspace-contract-review" aspire run --apphost src/Dse.AppHost/Dse.AppHost.csproj`. Existing `.artifacts/local-ingestion` remains untouched. This is Demo/Mock startup and does not configure Azure authentication or resources.
