## 操作

`dotnet run --project src/Dse.AppHost` はローカルの永続正本・Blob・Queueとfake AIを使う。Aspireが `Ai__Mode=Mock`、`AiUsage__Stopped=false`、`AiUsage__MaxOutputTokens=3000` を明示する。外部送信や料金は発生しない。API/Workerを単独で起動する場合は、[Office取込手順](document-ingestion.md)に加え同じAI設定が必要。Live設定・実送信には[AIアダプター手順](ai-adapters.md)の承認・予算・opt-inを別途満たす。

1. 本人用のdocx/xlsxを「職歴・スキル」または「事例」としてアップロードする。「部署週報」は `departmentActivity` になり、本人や所属者の経験には加算しない。
2. 機械抽出後、永続 `enrichment` ジョブを通知する。管理表示で構造化・分類の成否、根拠ID、モデル・プロンプト・分類体系・データ版、試行数・トークンを確認できる。`fixture（fake AI）` と `実AI処理` を区別する。固定seedのfixtureはAI実行履歴を持たず、mockによる新規生成は `origin=mock` とAiRunを持つ。
3. 「プロフィールを更新」で経験・日付・分類を読み込む。説明・表示名・期間・参加可否を訂正し、保存する。`If-Match` と `Idempotency-Key` を必須とし、他人の訂正・古いETagを拒否する。
4. 再投影完了後、手動一次検索で確認する。根拠検証済みのAI抽出値は `ai_unconfirmed` のまま検索できる。未確認を検索結果にも表示する。
5. 「公開を撤回」で人物の有効版を即座に外す。通常メンバーへの人物読取も止める。参加不可は検索候補から除外するが公開状態とは別。明示的な「再公開する」まで再取込で公開を復活させない。原本文書のACL変更・文書削除とは別操作である。

`web/tests/fixtures/profile.docx` と `profile.xlsx` は、機械設計2019-01-01〜2023-01-01、ソフトウェア開発2023-01-01〜2026-01-01の架空職歴。`generate.py` で再作成できる。評価用 `evaluation/documents/tuning.*` は複数人物・事例を含む資料であり、本人プロフィールの一括登録には使用しない。

## 抽出と正本

- 日付・セル値は機械抽出を優先する。Word表・Excelの同一行は位置情報でまとめ、各元段落・セルのEvidenceRefを保持する。説明中の明確なISO日付範囲から月数をコードで算出し、人物合計は重複期間を除く。年数の自由記述だけ、曖昧な日付、複数の期間が混在する断片はNULL/unknown。日付範囲は終了日を含まない経過月数として扱う。
- 機械処理で期間を確定できない非定型の単独段落のみFoundryのJSON構造化ポートに渡す。主張が参照元の実在IDに結びつき、本文に完全一致する抽出引用であることを照合する。意味の推測・言い換えを根拠一致と見なさない。原文の説明を正本に残し、構造化結果は検証用途に使う。
- 本人資料という登録先はサーバー認可で決める。本文内の社員IDや命令は権限を変えない。複数人の職歴を1人へ取り込む用途は対象外。
- 人物全体・経験断片（部署実績は全体・事例断片）ごとにJevを呼び、6カテゴリ全分布、Choice、別Confidence、分野ごとのNoulを保存する。未評価・情報不足はNULL、明示的な経験なしの判定はsupported/0で区別する。Probabilityを経験年数・熟練度に変換しない。
- 正規化語、スキルID、分類体系版、公開範囲、参加可否をSearchUnitへ投影する。閾値は検索条件として保存分布へ適用するため、閾値変更でJevを呼ばない。本人訂正後は変更されたテキストを再分類する。入力・根拠・モデル・プロンプト・分類体系が変わらなければ保存分類を再利用する。

## 副業務の検索断片（Issue #30・試験用）

`Profile:SecondaryWorkFragments=true`（環境変数`Profile__SecondaryWorkFragments=true`）で、元の経験断片を残したまま副業務の検索断片を追加する。AppHostとPlaywrightのダミー環境では有効。設定省略時は無効で、Live設定や既存のクラウドデータへの適用は今回行っていない。

句点・改行等の境界に続く「副業務として」「副業務は」「副業務：」「兼務として」「兼務は」「兼務：」以降を、`secondary-work-v1`の機械処理で原文から抜き出す。共同実施・補助・経験なし等の文脈は削除しない。追加本文が参照元の単一EvidenceSpanに完全一致する引用である場合だけ、独立にJev分類してSearchUnitを追加する。分類指示と検索閾値は従来のものを使う。

これは検索用の派生断片で、本人が編集する経験正本・経験月数は増やさない。元の人物ID、確認状態、公開範囲、根拠ID・版を引き継ぐ。同じ入力・根拠・モデル等での再投影は保存分類を再利用する。本人訂正で副業務を削除したら、次の投影に派生断片を含めない。原本にない本人の追記は元断片として扱い、原本引用として派生断片へ追加しない。撤回・元資料の利用不可・版変更は既存の正本照合で派生断片にも反映する。

元経験＋派生検索断片で20件まで（人物全体の投影は別）。超過は`PROFILE_FRAGMENT_LIMIT`で確認待ちとし、部分公開しない。新規派生断片の分類は追加のAI処理となるため、Live時には既存の予算制御・送信条件が適用される。

明示見出しがない任意の職歴文、複数EvidenceSpanにまたがる副業務、複数副業務を個別に分ける処理は対象外。既存プロフィールは自動で一括再投影せず、次の取込・本人訂正に伴う投影から適用する。[ローカル試験とダミー原本](validation-results/20261003-issue-30-secondary-local/results.md)を参照。先行の保存応答比較では共同実施の前置きを外していたため、後続で[文脈と原本根拠を保持した40入力の実Jev計測](validation-results/20261003-issue-30-jev/results.md)を行った。既観察の確認集合で人物Recall85%→100%を確認したが、独立集合・実Cosmos・最終LLM品質・本番採用は未完了。

## 版・再取込・復旧

同一所有者の「文書種別＋文書名」を取込系列として、受理した最新文書IDをPersonに保存する。同じ系列は元段落/行の位置で経験IDを安定化する。古い系列のジョブは `SOURCE_REVOKED` で中止する。文書名変更や行移動は別系列/断片になるため、同じ資料の更新では文書名・位置を維持する。

本人訂正・本人確認済みの断片を再取込で上書きしない。新しい記載が矛盾した場合は `correctionState=conflict` と `pendingExtraction` に候補を残し、現在の本人記載を検索する。原本から消えた未訂正断片は有効な経験一覧から外す。本人訂正済み断片の削除は差分確認に残す。「内容を本人確認」または該当断片の再訂正で、本人記載を維持したまま差分を解消する。

AI実行中は正本を公開しない。新しい経験・分類・全投影・有効版・完了Jobをcatalogの同一トランザクションで確定する。確定直前に人物・文書・根拠・分類のETagとJobリースを照合するため、途中停止、訂正、撤回、旧通知が混在しても部分公開しない。入力が変わった処理はcancelledになり、最新の原本・本人状態を確認して管理画面から再実行できる。

初期処理上限は1人物/部署実績20断片、1原本100根拠、連結本文8,000文字。超過は `PROFILE_FRAGMENT_LIMIT` / `PROFILE_TEXT_LIMIT` で確認待ちとし、一部だけ取り込まない。既存AI入力・出力・処理時間の上限も適用する。Jevの全分布＋分野別Noulには出力上限3,000を設定する。Liveでは承認済みのモデル上限・予約費用にも適合させる。

通知漏れは `--reconcile` で `ingestion` / `enrichment` / `projection` の未完了ジョブを再通知する。Workerは同じETagリース・不可視期限更新・有限再試行を使う。AI停止/予算停止は `budget_stopped`、不正JSONや根拠不一致は `needs_review`。依存障害はバックオフ後最大3回、上限後failed/poison。復旧後の再実行はETag付きの明示操作で、supersedesJobId付きの新Jobを作って過去の失敗履歴を保持する。queuedの再通知は同じJobを使う。`--jobs` で各種ジョブを確認できる。
