# 候補一覧の読取り取消と根拠共有

## 概要

`GET /api/v1/skill-candidates` の取消で、読取り専用処理の終了を証明できる場合だけfenceを解放する。既存の汎用取消・不明な書込み・未終了writerは引き続きfail closedとする。既に残留しているfenceは自動解除せず、[正式復旧手順](persistence.md)を使う。

## 終了を証明する境界

- `ReadOnlyFencedResult` が認可の再照合、候補一覧の構築、HTTP応答のシリアライズを同じfenceで実行する。
- `FencedReadPhase` のrepositoryだけで根拠を読み、業務Commitの試行を禁止・記録する。要求内のread/queryと応答streamのwrite/flushの未終了数を追跡する。
- 要求tokenが取消済み、書込み試行なし、追跡中I/Oが0、入れ子処理にも不明結果がない場合に限り、安全な読取取消として扱う。
- 正常終了に見えても未終了I/Oがあれば`READ_OPERATION_INCOMPLETE`で閉じる。遅れてI/Oが終了しても自動解除しない。依存例外、未要求の取消、不明結果、解放Commitの失敗も閉じたままにする。
- HTTP応答の終了はstreamのTask契約上の終了を指す。既に送信した文字列の回収、任意の非協調プロセスやSDK内部動作の終了までは保証しない。応答writerを待たずに解放しない。

汎用`FencedResult`を一括変更しない。今回の適用は、書込みやAI呼出しをしないことを確認した候補一覧だけ。他の応答への適用は、その経路の副作用と終了条件を個別確認する必要がある。

## 一覧内の共有

同じactor・tenant・fence・1ページの中だけで、fragment IDごとの`ReadSource`結果を共有する。全span、原本・文書版・親generation、ACL、fingerprintの検証は最初の取得で維持する。読取専用repositoryは同じIDのレコードをコピーして再利用する。

次ページ、別要求、別actor、AI待機を跨いで再利用しない。次の要求は新しいACL／ETag／原文を読み直す。撤回・削除・権限外は隠し、古い提案は引用を返さず再収集待ちにする既存動作を維持する。人物経験、辞書、評価gold、技術列の意味は変更しない。

## 検証と運用上の制限

HTTPの構築中／応答中の取消、未終了read／writer、書込み試行、不明結果、同時writer、原文版変更・権限境界と要求間キャッシュの不在をモック／TestServerで検証する。実AIは不要で、保存済み業務結果を再抽出しない。

同一fragmentを共有する候補が2件ある回帰では、fragment読取りを1回に制限する。実環境の通信回数や処理時間の改善率は、このローカルテストから推定しない。

今回の修正は既存fenceレコードの移行、予算補充、復旧権限追加を含まない。旧ソースへのロールバックは可能だが、残留fenceの復旧は別の明示的な運用判断が必要である。
